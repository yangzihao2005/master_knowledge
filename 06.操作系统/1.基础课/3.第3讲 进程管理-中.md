# 操作系统基础课 第3讲 进程管理-中

## 进程间通信的含义

[00:00:00 - 00:12:00]

进程间通信（IPC）指一个进程与另一个进程之间进行数据交换。本讲分两大块：进程通信与处理机调度。之所以只有"进程间通信"而没有"线程间通信"的说法，是因为同一进程内的线程共享地址空间，T1 写入内存的数据 T2 可以直接取到，本身不存在隔离带来的传递困难。进程则各自拥有独立的地址空间，一个进程写入自己内存的数据另一个进程无法访问，才需要专门的通信机制。

> **定义**：进程间通信是指进程与进程之间进行数据交换的过程。

## 进程间通信的必要性与四种方式

[00:12:00 - 00:15:00]

以 MP3 播放软件为例，核心功能是"读文件→解压缩→播放"，若分别写成 P1、P2、P3 三个进程，则 P1 读出的数据必须交给 P2，P2 解压的结果必须交给 P3，数据要在进程之间逐级流通。难点在于三个进程的地址空间彼此隔离，P1 只能访问自己那块内存；寄存器又不能长期保存数据，因此必须借助内存传递，却恰恰无法直接共享内存。解决思路由此分成四类：共享存储系统、消息传递系统、管道系统、信号系统（信号为近年考纲新增）。

> **易错点**：进程隔离的根源不是"内存不够"，而是各自的虚拟地址被映射到不同的物理内存单元；各种通信机制本质上都是在处理或利用这一映射关系。

## 共享存储的实现原理

[00:15:00 - 00:20:00]

思路是修改映射关系：让 P1 与 P2 的某些虚拟地址映射到同一块物理内存单元，即"同映射"。例如 P1 的 4 号逻辑单元与 P2 的 3 号逻辑单元都映射到物理块 2，则 P1 往 4 号写入 B，P2 从自己的 3 号单元即可读出 B。要点是两边的物理块号必须相同，而它们使用的逻辑地址不必相同。实际系统中共享的单位是页或段，通过调整两个进程的页表，把不同的逻辑地址映射到同一物理页。

> **定义**：共享存储系统——让不同进程的若干逻辑地址映射到同一块物理内存区域，以此实现数据交换。
> **易错点**：共享的是物理内存，不是虚拟地址；共享双方使用的逻辑地址可以不同，但必须映射到同一物理块。共享区一旦建立，双方都能读写，就必须引入同步互斥来保证正确性。

## 共享存储的建立、访问与释放

[00:20:00 - 00:26:00]

Linux 下共享存储有两种实现：mmap 借助文件（内存映射文件）实现，留到文件系统部分再讲；shared memory 以内存为中介，是本课重点。建立分三步：先由发起通信的一方通过系统调用创建（划定）一块共享内存区域，然后通信双方各自通过系统调用把自己的某个逻辑地址链接到这块物理内存上，此后即可通信。访问时因为共享内存位于进程自己的用户地址空间，直接用虚拟地址读写即可，不必陷入内核、不一定切换特权级。释放时，双方断开链接并不会回收该内存，还要再调用专门的系统调用取消其"共享内存"身份，这块内存才被彻底释放。

> **易错点**：只有"创建共享区""链接/断开链接"需要系统调用，真正传输数据时不需要操作系统参与。

## 内核空间的共享与内核缓冲区

[00:26:00 - 00:29:00]

内核代码和数据由 PBR 从磁盘引导进内存，全系统只有一份；但每个进程的地址空间都由用户空间和内核空间两部分组成。各进程的内核空间使用相同的逻辑地址区间，映射到同一块物理内存（内核区），相当于以共享存储的方式把内核共享了。于是内核天然可以充当中介：在内核中分配一块多进程均可读写的区域，即内核缓冲区，进程便可通过它传递数据。

> **定义**：内核缓冲区——内核中分配的多进程可读写的内存区域，用作进程间通信的中介。
> **易错点**：用户空间彼此不同、不能直接传数据；能借用的"公共地带"是共享的内核空间。所谓"缓冲区"之所以人人可访问，原因即在此。

## 消息传递系统与信箱

[00:29:00 - 00:34:00]

信箱是保存通信消息的实体，位于内核区，各进程 PCB 中保存自己信箱的位置。信箱分三类：私有信箱（每进程一个，只接收发给本进程的消息）、公共信箱（内核所有，所有进程都可访问）、共享信箱（由某进程创建并通知指定进程共同使用）。直接通信方式把消息直接投递到目标进程的私有信箱，系统调用参数为 message 与目标进程号；接收方以发送者为参数到自己的信箱中查找。间接通信方式把消息放入公共或共享信箱，发送参数为 message、信箱号与目标进程，接收方以信箱号与发送者为参数取信。发送方之所以"知道"对方信箱在哪，是因为陷入内核后由操作系统查 PCB 完成投递。

> **易错点**：直接通信以"进程"为地址，间接通信以"信箱"为地址；两者能成立的根本原因仍是内核空间共享。

## 管道通信的原理与容量管理

[00:34:00 - 00:44:00]

管道使用内核中的一块内存区域，以环形缓冲区（即循环队列）组织，数据只能从队尾写入、从队头读出。四个特点：每个数据只能读一次，读走即失效（因此更准确的说法是"取走"而非"读"）；结构为环形缓冲区；只能读当前读指针所指、写当前写指针所指的位置；读空管道或写满管道的进程都会被阻塞。实现上用两个累计计数器：nread 为管道创建以来的总读取数，nwrite 为总写入数，当前读位置为 nread mod N、写位置为 nwrite mod N（N 为容量，例中为 16），每读写一次计数器加一，但计数器本身不取模。判满为 nwrite − nread = N，判空为 nwrite = nread。

> **公式**：读位置 = nread mod N；写位置 = nwrite mod N；满 ⇔ nwrite − nread = N；空 ⇔ nwrite = nread。
> **易错点**：nread、nwrite 是"从创建到现在的累计次数"，不是指针；指针位置只能由累计值取模得到。

## 管道的文件抽象与访问权限

[00:44:00 - 00:47:00]

在 Linux 中管道通常被抽象成文件，创建管道会得到两个文件描述符：F1 为读端、F2 为写端。对 F1 执行读、对 F2 执行写，会被虚拟文件系统转换为对管道的读写，具体读写位置由管道内置的读/写指针决定。进程对管道有两种权限：readable 与 writable，多数与该管道无关的进程两者皆无，权限在管道创建时随继承关系确定。

> **易错点**：管道的读端写端是同一内核缓冲区的两个"接口"，不是两块独立数据区。

## 管道的半双工特性

[00:47:00 - 00:54:00]

通信分三种：单向（只能 A→B 或 B→A）、双向/全双工（可同时双向传输）、半双工（可双向但不能同时）。管道属于半双工：P1 向 P2 传完之后，P2 才能反向传。若违反这一点、双方同时向管道写入，P1 在读的时候可能把自己先前写入的 A 又读回来，A 随即失效，信息永远无法送达 P2，通信失败。但半双工并不要求"P1 全部写完 P2 才能读"：P1 只写、P2 只读，二者可以并发进行，因为管道的读写指针顺序保证了数据不会乱序。

> **易错点**：半双工限制的是"同一时刻只能有一个传输方向"，不是"必须整批传完才允许对方读"。

## 管道的继承与引用计数

[00:54:00 - 00:59:00]

匿名管道只能通过父子进程继承获得访问权限，子进程完全继承父进程的权限（可读可写、只读或只写），因此管道通信本质上是有亲缘关系进程之间的通信。读端、写端各有一个引用计数，表示有多少进程拥有该端的权限；某进程释放自己的写权限时写端计数减一。计数减到 0 时写端关闭，且是永久关闭：管道的写权限只能由继承获得，当前已无任何进程持有写权限，之后新建的进程也不可能再获得。

> **易错点**：写端关闭是"永久"而非"暂时"——没有重新打开管道的接口，权限来源只有继承。

## 管道的关闭、释放与互斥访问

[00:59:00 - 01:02:00]

读端引用计数为 0 时同样直接关闭，不必考虑"以后可能还有进程要读"。若读端已关闭，写入的数据已不可能被取走，此时提前释放管道也是合理设计。多进程读写同一管道时，管道内部有互斥锁，读管道、写管道都必须在同步互斥下进行，否则会出现前述数据被自己读回的错误。除匿名管道外还有命名管道，可在无亲缘关系的进程之间通信。

> **易错点**：管道与生产者—消费者问题的规则完全一致，两者的同步互斥要求可以放在一起理解。

## 通信的约定与常见辨析

[01:02:00 - 01:11:00]

共享存储、消息传递、管道三种方式都以"中介"为核心，接收方必须知道去哪里取数据，这靠通信双方事先的约定：数据写到哪个管道/共享区/信箱、采用什么格式，由编写两个进程的程序员商定，或由同一程序员在两端保持一致。辨析一：共享存储用虚拟地址直接访问、不必切换特权级，只有消息传递和管道借助内核缓冲区，两种说法针对不同方式，并不矛盾。辨析二：管道权限创建时即确定，不能修改，只提供关闭接口、没有打开接口。辨析三：同一管道在同一时刻不允许多个进程同时写或同时读；子进程对管道的权限只能少于或等于父进程。

> **易错点**："通信不一定切换特权级"只对共享存储成立，不能推广到消息传递与管道。

## 信号机制的基本模型与来源

[01:11:00 - 01:15:00]

信号传递的往往不是数据，而是"你需要做某种处理"的通知。基本模型是：进程正在运行或等待时，其他进程或操作系统向它发出信号，进程通过某种机制检测到后作出响应，例如在终端按 Ctrl+C 会向相关进程发出终止信号。信号来源分四类：用户的特定行为（如 Ctrl+C）、系统调用（Linux 的 kill 是"发信号"而非"杀死"，可向指定进程发送编号为 K 的信号）、硬件异常（如除零，由异常处理程序发出信号）、软件条件（如读写已关闭的管道，内核发送 SIGPIPE）。

> **易错点**：kill 系统调用的语义是"发送信号"，不是"终止进程"。

## 信号的种类与收集

[01:15:00 - 01:18:00]

类 Linux 系统共有 64 种信号，编号 0~63，其中 0~31 为缺省信号，32~63 为用户自定义信号。每个进程的 PCB 中有两个相关字段：信号接收字（long 型，64 位，每一位对应一个信号编号）与信号掩码 sigmask。发送信号时，操作系统把目标进程接收字中对应比特置 1；进程只处理"接收字对应位为 1 且掩码对应位为 0"的信号，即已收到且未被屏蔽的信号。

> **公式**：处理条件 = 接收字[K] = 1 且 sigmask[K] = 0。
> **易错点**：接收字记录"是否收到"，掩码记录"是否屏蔽"，是两套独立的位图，不能混为一谈。

> ⚠️ **需回看视频 [01:16:00]**：PCB 字段名"receive"疑为 ASR 误记，教材通称"信号接收字/未决信号集"，需核对标准术语 —— "它的 PCB 当中都有两个字段，一个叫 receive，一个叫 sigmask。"

## 缺省信号与用户自定义信号

[01:18:00 - 01:21:00]

缺省信号（0~31）的处理方式由操作系统规定，处理在内核态完成，用户无法修改，例如 9 号 SIGKILL 表示立即终止进程。自定义信号（32~63）的含义与处理由用户进程自己决定，类似用户态下的中断处理：进程通过 sigaction(信号编号, 处理函数) 注册，处理函数位于用户空间，注册后在信号注册表中增加一个表项，收到该编号信号时调用对应函数。

> **定义**：缺省信号——由操作系统定义并处理的信号，处理在内核态完成。自定义信号——由用户注册处理函数的信号，处理在用户态完成。
> **易错点**：自定义信号的处理函数在用户态执行，但跳转与返回都由内核完成（见下一条）。

## 信号处理的完整流程

[01:21:00 - 01:25:00]

进程原本在用户态运行，因中断或异常进入内核态处理。中断/异常处理完毕、准备返回用户态之前，内核先检测并处理缺省信号，再检测是否有自定义信号。若有自定义信号，则修改中断返回的断点（保存的 PC 值），使其指向该进程注册的信号处理函数；随后按正常流程恢复现场返回用户态，实际就开始执行处理函数。处理函数末尾有一条"信号返回"系统调用，它重新进入内核、恢复原本的断点，再次返回用户态从原位置继续执行。

> **易错点**：必须以中断/异常为起点，因为只有进入内核态才能完成信号的检测、断点修改与跳转；自定义信号不是"在用户态自己轮询"发现的。

## 信号机制问答与除零异常案例

[01:25:00 - 01:35:00]

发送方只有两类：操作系统（在处理中断、异常或系统调用的过程中发出）与其他进程（通过 kill）；收集方式是在 PCB 的信号接收字中记录。不同进程对同一缺省信号的处理方式相同，对同一自定义信号的处理方式可以不同。除零时，触发的异常类型（除零异常）由硬件决定，随后发出的信号类型由操作系统决定。要让各进程对同一异常有不同处置，做法是：OS 在除零异常处理程序中向当前进程发送一个自定义信号（如 55 号），各进程事先为 55 号注册各自的处理函数，于是 P1、P2 虽经历同一异常处理流程，却调用各自的处理函数（C 程序通常直接终止，Java 可自行捕获处理）。

> **易错点**：异常类型由硬件决定、信号类型由 OS 决定，这一对常被互换来设置选择题干扰项。

## 调度的三个层次

[01:35:00 - 01:41:00]

作业调度（高级调度）根据作业控制块中的信息审查系统能否满足作业的资源需求，按一定算法从外存后备队列中选作业调入内存，为其创建进程、分配资源并插入就绪队列。中级调度（内存调度）在内存紧张时把进程换出到外存挂起，空间足够时再换入，只引起进程状态变化（就绪↔挂起就绪、阻塞↔挂起阻塞），PCB 始终存在。进程调度（低级调度）从内存就绪进程中选一个分配处理机，是最重要的一级。作业调度与中级调度都涉及内外存交换，但作业调度是进程"从无到有"，一个进程一生只经历一次；中级调度只改变状态。

> **定义**：作业——多用户系统中用户提交任务的基本单位，由作业控制块 JCB 描述；一个作业可要求创建多个进程，故作业与进程不一定是 1:1。

## 处理机调度与调度器

[01:41:00 - 01:44:00]

处理机调度指在多道程序系统中，从就绪队列按一定算法选择一个进程并把处理器分配给它运行；若系统支持线程，则处理器调度的实际对象是线程，408 不严格区分进程调度与线程调度。调度器维护所有就绪队列、调度算法、进程切换方法，以及 current_proc（始终指向当前进程：切换前指向被换下者，切换后指向被换上者）。当就绪队列为空时，由闲逛进程（idle）占用 CPU 防止空转。

> **易错点**：闲逛进程优先级最低，只要还有任一就绪进程就不会上 CPU；它通常只有一条指令，除 CPU 外不需要其他资源，因此不会被阻塞。

## 非抢占式调度与协作式调度

[01:44:00 - 01:47:00]

非抢占式调度中，进程除非运行结束或主动放弃 CPU，否则不会被其他进程抢占；调度时机就是运行结束或主动放弃（因等待 I/O 等而阻塞、或因退出而放弃）。yield 系统调用让当前进程主动进入就绪态、把 CPU 让给别人；完全依靠进程自觉让出 CPU 的方式称为协作式调度。非抢占式调度不频繁、CPU 利用率一般更高、系统开销小，但实时性差，适用于批处理系统，不适用于多数实时与分时系统。

> **易错点**：进程"主动进入就绪态"是存在的（yield），不要以为让出 CPU 只有阻塞和结束两种途径。

## 抢占式调度的实现

[01:47:00 - 01:55:00]

抢占式调度中，进程可能因时间片用完或有更高优先级进程进入就绪态而被强行换下，特点是调度频繁、实时性强。实现方式是在 PCB 中增加 need_resched 标志，并在中断/异常处理完毕、准备返回用户态之前做一次检查：need_resched 与 can_reschedule（进程的固有属性，表示是否允许被调度）相与为 1 才发起调度，否则直接中断返回。need_resched 的置位时机有两个：一是有进程进入就绪态（阻塞→就绪，或被创建）且其优先级高于当前进程 current；二是时钟中断处理中时间片减一后变为 0。被抢占的进程自身回到就绪态。

> **易错点**：抢占发生在"中断返回前"这个检查点，而不是事件发生的瞬间；比较的是新就绪进程与当前进程的优先级。

> ⚠️ **需回看视频 [01:48:00]**：抢占标志名转写前后不一致，"need rescue"与后文"need reschedule"应为同一字段，需确认标准写法 —— "我们需要在我们的PCB里面增加一个标识，叫need rescue……判断我这个 need rescued，就是我是不是需要被调度。"

## 不能被调度的情况

[01:55:00 - 01:58:00]

有三种情况不能进行调度：当前进程正处于中断处理过程中；进程处于操作系统的内核程序临界区中；正在屏蔽中断的过程中。实现上就是把 can_reschedule 置 0，此时无论 need_resched 是否为 1 都不会切换。这三条与前后知识体系关联较弱，建议直接记忆，但真题确实会考。

> **易错点**：第三条辨析常设陷阱——必须是"内核程序"且"临界区"两个条件同时满足，只说"进程在临界区中就不能调度"是错误的。

## 调度性能指标

[01:58:00 - 02:02:00]

CPU 利用率 = 进程实际运行时间 / 总时间，中断处理、调度与进程切换等开销都不算实际运行时间。系统吞吐率 = 单位时间内完成的作业数。周转时间 = 作业从提交到完成的时间间隔，平均周转时间取均值；带权周转时间 = 周转时间 / 实际运行时间，平均带权周转时间再取均值。等待时间 = 进程从创建到完成处于就绪态的时间之和，即等 CPU 的时间，不受执行时间与 I/O 时间影响，只取决于调度算法。响应时间 = 从用户提交请求到系统首次响应的时间间隔。

> **公式**：带权周转时间 = 周转时间 / 运行时间；等待时间 = Σ（就绪态持续时间）。
> **易错点**：等待时间只统计"就绪"，阻塞等待 I/O 的时间不计入。

## 先来先服务（FCFS）

[02:02:00 - 02:04:00]

按进入就绪队列的先后顺序上 CPU，属非抢占式。例：P1、P2、P3 运行时间分别为 12、3、3，若按 P1→P2→P3 到达则依次执行；若到达顺序变为 P2→P3→P1，平均周转时间明显更短，说明 FCFS 对短进程不利。其优点是简单，缺点是平均等待时间波动大、I/O 资源与 CPU 利用率低：CPU 密集型进程长期占用 CPU 时 I/O 设备闲置，I/O 密集型进程只能干等。

> **定义**：CPU 密集型进程——执行过程中使用 CPU 的时间占比高；I/O 密集型进程——I/O 时间占比高。
> **易错点**：FCFS 看似公平，实则没有考虑各进程对服务时间的长短诉求，并不公平；理想做法是让 CPU 使用时间短的进程先上，而 FCFS 做不到。

## 优先级调度

[02:04:00 - 02:07:00]

按优先级高低选择进程。静态优先级在进程创建时确定、运行期间不变；动态优先级在执行过程中可以调整。常见设置原则：计算密集型（CPU 密集型）的优先级低于 I/O 密集型，后台进程低于前台进程，用户进程低于系统进程。按是否抢占又分两种：非抢占式在调度时比较优先级，进程一旦上 CPU 即使有更高优先级进程就绪也不让出；抢占式则在调度时选就绪队列中优先级最高者，且新进程进入就绪态时若优先级更高可立即抢占。

> **易错点**：静态/动态优先级与抢占/非抢占是两个独立维度，可以组合（如静态优先级的抢占式调度）。

## 短进程优先（SPN）

[02:07:00 - 02:11:00]

就绪队列按预期执行时间排序，每次选择执行时间最短的进程投入运行，通常为非抢占式。其最大优点是可以证明具有最优的平均周转时间：若把后面的短进程与前面更长的进程交换位置，总周转时间只会增加。缺点有二：一是可能导致饥饿，短进程连续到达时长进程长期得不到 CPU；二是需要预知运行时间，而进程为了更早获得调度可能虚报（把 10 说成 1），因此它只是理论上的理想算法。其可抢占版本称为短剩余时间优先（SRTN）。

> **定义**：饥饿——进程因调度策略长期得不到所需资源（此处为 CPU）而无法推进。
> **易错点**：考题按题目给定的运行时间计算即可，不必考虑进程虚报；SPN 的"最优"仅指平均周转时间。

## 短剩余时间优先（SRTN）例题

[02:11:00 - 02:15:00]

SRTN 是 SPN 的可抢占版本：新进程就绪时，若其所需执行时间小于当前进程的剩余执行时间，则抢占当前进程；每次调度选择剩余时间最短者。解题方法是画甘特图：以"进程到达时刻"和"进程完成时刻"为关键时间节点，每到一点就比较当前进程剩余时间与新到进程所需时间。例题（P1~P4 到达时刻 0/2/4/6，运行时间 10/7/6/9）：2 时刻 P1 剩 8 > P2 的 7，P2 抢占；4 时刻 P3(6) 不敌 P2(5)；6 时刻 P4(9) 不敌 P2(3)；P2 于 9 结束，之后按 P3、P1、P4 的顺序执行完，完成时刻分别为 15、23、32；周转时间 23、7、11、26，平均 16.75。

> **公式**：周转时间 = 完成时刻 − 到达（就绪）时刻；平均周转时间 = Σ周转时间 / 进程数。
> **易错点**：比较对象是"新进程所需时间"与"当前进程剩余时间"，不是与当前进程的原始总时间比较。

## 最高响应比优先（HRRN）

[02:15:00 - 02:18:00]

响应比同时考虑等待时间与计算时间，定义为 (等待时间 + 要求服务时间) / 要求服务时间，即 1 + 等待时间/要求服务时间。等待时间越长响应比越高，计算时间越短响应比也越高，因此它既让短进程先上，又缓解了长进程的饥饿问题，属非抢占式算法。按例中数据（已等待 5、6、10，需 CPU 5、9、7）计算，三者响应比为 2、1.67、2.43，最高者应为 P3。

> **公式**：响应比 R = 1 + 等待时间 / 要求服务时间。
> **易错点**：响应比是"等待时间与服务时间"的综合指标，不能只比等待时间或只比服务时间。

> ⚠️ **需回看视频 [02:17:00]**：例题数据与结论矛盾（按给定数据最高响应比应为 P3，转写称 P2），疑为数据口误或 ASR 数字错误 —— "那它们的响应比，哎，打错字了啊……那此时 P2 的响应比最高，那 P2 就上 CPU。"

## 时间片轮转（RR）

[02:18:00 - 02:26:00]

RR 是 FCFS 的改进：就绪进程排队，每个进程每次最多运行一个时间片，时间片用完即被剥夺并排到队尾。它依赖时钟中断来计时与扣减时间片。例：P1~P4 需 53、8、68、24，时间片 20，则执行序列为 P1(20)、P2(8，完成)、P3(20)、P4(20)、P1(20)、P3(20)、P4(4，完成)、P1(13，完成)、P3(28，独占至完成)；某进程的等待时间即其各段就绪时间之和。时间片长度要折中：太短则频繁上下文切换、开销压过有效工作；太长则退化为 FCFS 且长进程等待过久。经验上应使上下文切换开销占系统总开销的 1% 以内。

> **易错点**：RR 属于抢占式调度（时间片到点由操作系统强行换下），不是进程自愿让出；其开销主要来自上下文切换。

## 时钟中断

[02:26:00 - 02:30:00]

时钟中断属于外中断，由计算机中的计时器按固定间隔发出中断信号触发。间隔长短由操作系统用特权指令设置，可以动态修改，改后下一次中断就按新间隔到来。时钟中断是进程感知时间的基本方式：时间片扣减、进程已运行时长、系统时间，以及一切与时间相关的算法（最典型的是时间片轮转）都要靠时钟中断推进和更新。

> **易错点**：时钟中断的间隔 ≠ 时钟周期。时钟周期是 CPU 的硬件特性，时钟中断间隔可由指令设定，二者相关但绝不等同。

> ⚠️ **需回看视频 [02:27:00]**：计时器示例中"毫秒"与"纳秒"混用，时间单位表述有误，需确认原意 —— "我假设我计时器，我让它每两毫秒，每每两纳秒中断一次。"

## 真题：引起进程调度的事件

[02:30:00 - 02:33:00]

题目问"下列事件中可能引起进程调度程序执行的是"：Ⅰ 中断处理结束、Ⅱ 进程阻塞、Ⅲ 进程结束、Ⅳ 进程时间片用完，答案为四项全选。Ⅱ、Ⅲ 使进程让出 CPU，必然触发调度；Ⅳ 时间片用完需换下当前进程；Ⅰ 之所以也成立，是因为抢占式调度把"中断返回前检查 need_resched 与 can_reschedule"作为调度时机。

> **易错点**：分析真题时每个选项都要能独立说出理由；因为已能选出答案就放过某一项，等于在真题里留漏洞。

## 多级队列与多级反馈队列

[02:33:00 - 02:36:00]

多级队列调度把就绪进程分到多个独立子队列，各队列有自己的调度算法，队列之间有固定优先级（如前台队列全部处理完才处理后台队列）；缺点是低优先级队列可能饥饿，且进程一旦入队就不再移动。多级反馈队列在此基础上允许进程在队列间移动，且时间片随优先级降低而增大。典型规则：当前时间片内未完成的进程被降级（说明它需要更多 CPU），I/O 密集型进程因占用 CPU 少而留在高优先级队列。

> **易错点**：多级队列"进程不能跨队列移动"，多级反馈队列"可以移动"，这是两者的根本区别。

## 多级队列调度综合题

[02:36:00 - 02:42:00]

题目：维护 Q1、Q2、Q3 三个就绪队列，优先级依次降低，队列内部均采用短进程优先，进程调度与切换开销 2ms，不考虑切换到首个进程的开销，所有调度均非抢占。解题先把各队列归属、到达时间、运行时间提取到草稿纸，再按关键时间点画甘特图，每次调度完成后补上 2ms 切换开销。调度规则是先看队列优先级，高优先级队列有人就选它，队列内部再比运行时间长短。以 P3 为例：5 时刻到达，12 时刻才开始执行，22 时刻完成，故周转时间 22−5=17，等待时间 12−5=7。

> **公式**：周转时间 = 完成时刻 − 到达时刻；等待时间 = 首次开始执行时刻 − 到达时刻（本题各进程只运行一次）。
> **易错点**：切换开销 2ms 必须计入时间轴，否则后续所有时刻都会算错。

## 多处理器调度：并发与并行、SMP

[02:42:00 - 02:45:00]

只有一个 CPU 时，多个任务只能轮流上 CPU，宏观上同时、微观上交替，称为并发；有多个物理 CPU 或物理核时，不同任务可以在同一时刻真正同时执行，称为并行。多处理机分两类：对称多处理机（SMP）各 CPU 地位相同、共享全部系统资源、访问权限相同，Windows、Linux 都属于此类，也是 408 主要研究对象；异构多处理机各处理机权限不同、未必共享全部资源，设计更复杂。

> **易错点**：并发是"轮流"，并行是"同时"，两者不能混用。

## 任务分配与负载均衡、处理器亲和性

[02:45:00 - 02:48:00]

任务分配有静态与动态两种：静态分配在调度之初就确定任务归属哪个 CPU，运行中不再改变；动态分配中任一任务都可能被任一 CPU 取走执行。多处理器调度要特别考虑两点：其一是负载均衡，让各处理机任务量尽量均衡，避免一核早已空闲、另一核仍在积压，从而最大化总体性能；其二是处理器亲和性，任务在某 CPU 上执行过后，该 CPU 的 cache、TLB 已缓存其数据与指令（局部性原理），同一任务回到同一处理机更易命中，因此应尽量让任务在同一处理机上完成整个生命周期。

> **易错点**：负载均衡要求"任务可以搬走"，处理器亲和性要求"任务尽量别搬"，二者相互矛盾，实际系统需折中。

## 单队列与多队列调度、进程窃取

[02:48:00 - 02:50:00]

单队列调度只维护一个公共就绪队列，各 CPU 自行从中取任务，任务无法选择进入哪个 CPU，因此天然属于动态分配。多队列调度为每个 CPU 维护自己的就绪队列，但它并不等同于静态分配，因为任务可以在队列之间迁移。当某 CPU 的队列为空时，可从其他 CPU 的队列取走任务，这一机制称为进程窃取，用于避免处理机空闲。

> **易错点**：判断"静态还是动态"的关键是任务能否在处理机之间迁移，而不是队列有几个。

## 多处理器调度性能指标

[02:50:00 - 02:55:00]

任务流时间指单个任务所需的时间（任务若被分割在多台处理机上执行则累加各段）。调度流时间 = 各处理机上任务流时间之和 = 所有任务执行时间总和，平均流时间 = 调度流时间 / 任务数。处理机利用率 = 该处理机上任务流时间之和 / 最大有效时间单位（全部任务完成所需时间）。加速比 = 各处理机忙时间之和 / 并行工作时间，即"单处理机串行耗时"与"多处理机并行耗时"之比。吞吐率 = 单位时间内完成的任务数。例：三处理机五个任务，任务流时间为 7、6.5、2、2、2，调度流时间 19.5，平均流时间 3.9，全部完成用时 7，则加速比 = 19.5/7 ≈ 2.79，吞吐率 = 5/7。

> **公式**：平均流时间 = 调度流时间 / 任务数；处理机利用率 = 本机任务流时间之和 / 全部完成时间；加速比 = 调度流时间 / 并行工作时间；吞吐率 = 完成任务数 / 总时间。

> ⚠️ **需回看视频 [02:52:00]**：例题各任务流时间与处理机利用率的对应关系依赖课件图，转写中"对于 P1 来说……也是六点五"与 T1=7 不一致，数据无法可靠复原 —— "对于P1来说，它是不是就是到这里也是六点五，对吧？对于 P2 来说，它就是七除以七，就是一。"

## 课后答疑
