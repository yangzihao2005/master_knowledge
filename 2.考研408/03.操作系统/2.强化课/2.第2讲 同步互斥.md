# 操作系统强化课 第2讲 同步互斥

## 本讲定位：PV 操作是 408 重中之重

[00:00:00 - 00:10:00]

本讲覆盖同步互斥全部考点，其中 PV 操作约占全课三分之二，其余为其他同步互斥问题与死锁。老师用 2025 考研的经历说明押题不可靠：24 年刚考过 PV 大题，25 年模拟卷把 PV 换成了文件系统，结果真题仍是 PV 大题。强化课只有四讲却要覆盖 80%~90% 的知识，节奏快、密度高，需要边听边思考而非只过一遍。

> **易错点**：由"去年考过 PV 大题"推断"今年不考 PV"是典型的押题心态，2025 年真实验证失效。

## 信号量的合法操作：只能初始化与 P/V

[00:10:00 - 00:13:00]

以某展览馆画展为例（馆内容量 2000 人，分普通票和学生票且学生票数量受限，出入口每次仅一人进出，要求用 PV 操作实现）展示两份真实错卷：答卷对信号量做了加减、比较大小、取反、逻辑运算。信号量除初始化外**只允许 P、V 两种操作**，做算术运算、比大小、取非、逻辑运算一律非法。这类答卷几乎零分——等于不会使用信号量；某教材课后题给出的"if + 比较"答案也是错的。

> **易错点**：把信号量当普通整型变量写 `if(s > 0)`、`s = s - 1`、`s = !s`。

## PV 问题的三类划分与基本 PV 问题

[00:13:00 - 00:15:00]

按题目特点把 PV 问题分三类：基本 PV 问题、带条件分支的 PV 问题、进阶 PV 模型（用模板套解）。基本 PV 问题的特征是**执行流确定**：每个进程走完流程时每一行代码都会被执行，途中只可能被阻塞、被唤醒后仍按原顺序往下走，不会改变执行路径。408 历年真题考过的 PV 题都属于基本 PV 问题。

> **定义**：基本 PV 问题——进程无分支、必经每行代码，仅可能阻塞而不会改变执行路径的同步互斥问题。

## 基本 PV 分析法：从"执行条件"推出信号量

[00:15:00 - 00:24:00]

以生产者-消费者为模板，五步法：①不考虑任何同步互斥，先写出每个进程自身的行为序列；②逐个行为分析"该行为**能够执行**需要满足什么条件"（是能执行的条件，不是不能执行的条件）；③把条件写成"某量 > 0"的不等式，左边的量配一个信号量，初值即该量的初始值；④在该行为之前 P 该信号量；⑤考察该量在何处增减，**增加处 V**。

生产者放产品需满足两个条件：缓冲区空闲（互斥）、缓冲区有空位。空位数 > 0 → `empty`，初值 n，取出产品后 V(empty)；`1 - 缓冲区中进程数 > 0` → `mutex`，初值 1，进程离开缓冲区后 V(mutex)。消费者取产品需缓冲区空闲（与前面是同一条件，复用 mutex，不另设信号量）与产品数 > 0 → `full`，初值 0，放入产品后 V(full)。

> **公式**：`empty = n`，`mutex = 1`，`full = 0`；生产者 `P(empty); P(mutex); 放入; V(mutex); V(full)`；消费者 `P(full); P(mutex); 取出; V(mutex); V(empty)`。
> **易错点**：同一个条件（如"缓冲区空闲"）只对应一个信号量，不能给生产者、消费者各设一个。

## 互斥信号量抽象为"锁"与 P 操作的顺序

[00:24:00 - 00:29:00]

互斥访问不必每次列不等式，统一抽象为锁：进临界区 P(lock)、出临界区 V(lock)，初值 1，即可保证同时只有一个进程进入。多个 P 的次序规则是**先 P 条件更苛刻的普通同步信号量，最后 P 互斥信号量 mutex**；顺序反了可能死锁（基础课已验证）。

> **易错点**：先 `P(mutex)` 再 `P(empty)`/`P(full)`，进程持锁等待，其他进程无法进入临界区，死锁。
> **易错点**：`V(mutex)` 与 `V(full)` 的先后一般无妨，但 P 的顺序必须满足上述规则。

## 进程合作问题：多进程同步的信号量配置

[00:29:00 - 00:40:00]

P1、P2、P3 分别通过独占设备输入 A、B、C（设备需互斥）；P1 算 x=a+b，P2 算 y=a×b，P3 算 z=y+c-a；最后由 P1 打印 x、y、z。按五步法：互斥只有输入设备一个 mutex；同步按"缺谁"逐条列——P2 算 y 需 A 已输入（`SA`，初值 0，输入 A 后 V、算 y 前 P），P1 算 x 需 B 已输入（`SB`），P3 算 z 需 A、C 已输入且 y 已算（复用 SA，另加 SY），P1 打印需 y、z 已算（SY、SZ）。

同一进程内部的先后（如 P1 自己已输入 A）不构成同步条件，无需信号量。关键陷阱：SA 被"算 y"和"算 z"两处 P，SY 被"算 z"和"打印"两处 P，都只 V 一次时只有一处能通过，必须 V 两次——**一个信号量被 P 几次，就要 V 几次**。

> **易错点**：漏掉"同一信号量被多个进程重复 P"的计数需求，导致只能放行一个等待者。

## 同步依赖图与前向边的裁剪

[00:40:00 - 00:46:00]

把三个进程的步骤按依赖关系画成有向图（不同颜色区分进程），每条边代表一个先后关系、也就是一个同步信号量（V 在起点事件之后、P 在终点事件之前）。若边 u→v 之外还存在 u→…→v 的通路，该边就是**前向边**，可以删去；删完后剩余的边才对应必需的同步信号量。本题中"输入 A → 计算 Z""计算 Y → 打印"两条是前向边，相应信号量属冗余，可省。信号量可以合并定义（多个一起赋 0 写在一行），伪代码不因此扣分，但每个信号量的作用、P/V 对应什么条件要写注释。

> **定义**：前向边——有向图中起点到终点另有更长通路可达的边，删除后不改变偏序关系。

## 自行车问题：死锁边界与"一个阻塞条件一个信号量"

[00:46:00 - 01:00:00]

箱子有 n 个位置（n>3），工人 1 放车架、工人 2 放车轮、工人 3 一次同时取 1 个车架 + 2 个车轮组装。死锁边界：全是车架、全是车轮、或 n-1 个车架 + 1 个车轮都会让工人 3 永远凑不齐，故不死锁条件是**车架数 ≤ n-2、车轮数 ≤ n-1**。

由此推前置条件：放车架要求"当前车架数 < n-2"（放入后最多到 n-2），对应 `eShelf = n-2-(车架数)`，初值 n-2，取走车架后 V；放车轮同理 `eWheel = n-1-(车轮数)`，初值 n-1。另有箱子互斥 mutex 与空位 `empty`（初值 n，工人 3 取出 1 架 2 轮时 V 三次，插入方各 P 一次）。工人 3 取货前 P(车架) 一次、P(车轮) 两次，放入方各自 V；题目"不包含锁"即省略 mutex。

> **易错点**：把上限条件直接当前置条件（写成"车架数 ≤ n-2 即可放"），会多放一个而破坏不死锁边界。
> **易错点**：想用 int 变量 + if 解决上限问题——上限不满足会阻塞，必须用信号量。

> ⚠️ **需回看视频 [00:59:00]**：讲"提高并发度"时称分开取车架/车轮可让车架达到 n-1，与前面"车架 ≤ n-2"的不死锁边界不一致，具体条件变化未展开 —— "如果它是先取车架再取车轮，这样就允许你车架达到N减一"

## 水果问题：盘子互斥与两组对称同步

[01:00:00 - 01:16:00]

桌上盘子每次只能放一只水果，爸爸放苹果、妈妈放橘子，女儿取苹果、儿子取橘子。爸爸-女儿与妈妈-儿子两组完全对称，只分析一组。放苹果的条件是盘子空（水果数 < 1），对应 `plate`（初值 1，放前 P、取走后 V）；取苹果的条件是有苹果（苹果数 > 0），对应 `apple`（初值 0，放苹果后 V、取前 P）。妈妈/儿子同理用 `orange`。条件写法不唯一（"空盘子数 > 0"与"水果数 ≤ 1"等效），只要能对应到唯一的阻塞条件即可。

> **易错点**：这种条件少、结构简单的题反而真题命中率高，不要因"太简单"而漏设信号量或写错 P/V 位置。

> ⚠️ **需回看视频 [01:04:00]**：疑似口误，"苹果数量大于一"应为"苹果数量大于零"（有苹果即可取） —— "女儿取苹果有什么限制条件？那当然就是苹果数量大于一了"

## 小球问题：多重上限与绝对值条件的拆解

[01:16:00 - 01:40:00]

盒子可放红、白两色球，P1 放红、P2 放白、P3 取红、P4 取白，拿盒/放盒需互斥（mutex）。约束：红 ≤ 60、白 ≤ 50、红+白 ≤ 70、|红-白| ≤ 30。每个"上限"条件转成一个"距离"信号量：`eRed = 60-红`（初值 60，放红前 P，取红后 V）、`distance1 = 70-(红+白)`（初值 70，放红/放白前 P，取红/取白后 V）、`eWhite = 50-白`（初值 50，放白前 P，取白后 V）。

绝对值条件拆成两支：红-白 ≤ 30 与 白-红 ≤ 30。放红只可能破坏"红-白 ≤ 30"，所以只设 `distance2 = 30-(红-白)`（初值 30）：放红前 P，取红后 V、放白后 V、取白前 P（白减少使该值减小）。放白只可能破坏"白-红 ≤ 30"，另设 `distance3 = 30-(白-红)`（初值 30）：放白前 P、取红前 P，取白后 V、放红后 V。取红还需"有红球"→ `r` 初值 0；取白需 `w` 初值 0。

> **易错点**：以为"同一个绝对值条件"只对应一个信号量——distance2 与 distance3 是两个不同的阻塞条件，必须分开设。
> **方法**：绝对值处理口诀——拆成两条不等式，每一步只问"这一步会破坏哪一条"，另一条不必管（它若被破坏，说明早就破坏了）。

> ⚠️ **需回看视频 [01:29:00]**：疑似口误，放入白球的第二个上限条件应为"红+白 < 70"（distance1），而非"白球加红球的个数小于三十" —— "然后第二个，白球加红球的个数小于三十"

## 带条件分支 PV 问题的特征

[01:40:00 - 01:41:00]

这类问题中进程会因当前条件不同而走不同执行路径，某些分支会跳过对应的 P/V。与基本 PV 的根本区别：if 的条件本身**不导致阻塞**，无论真假程序都继续往下走，只改变路径；而阻塞条件不满足就必须停住。判定依据由此确定为：会不会阻塞——会阻塞用信号量，只改路径用辅助变量。

## 读者-写者基本模型：读写锁与读者计数器

[01:41:00 - 01:48:00]

多个读进程可同时读，读写互斥、写写互斥。模板是一个读写锁 `rw`（初值 1）：写者 `P(rw) … V(rw)`。读者不必然每次都抢 rw——只有第一个读者（当前无人在读）需要 `P(rw)`，退出时只有最后一个读者 `V(rw)`；中间读者"趁东风"直接进入。用计数器 `current` 记录在读进程数，并为它配专用 `mutex` 保证互斥访问。

> **公式**：`current = 0`，`mutex = 1`，`rw = 1`；读者：`P(mutex); if(current==0) P(rw); current++; V(mutex); 读; P(mutex); current--; if(current==0) V(rw); V(mutex)`。
> **易错点**：对 current 的每一次读写都必须包在 mutex 内；漏掉"最后一个读者释放 rw"会让写者永久饥饿。

## 信号量与 int 辅助变量的本质区别

[01:48:00 - 01:52:00]

三条区别：①信号量只能初始化、P、V；int 可做任意算术与判断。②信号量与"一种会导致进程阻塞的执行条件"一一对应，缺一个条件就多一个信号量；int 只作分支依据，取值如何都不阻塞，只形成不同路径。③信号量数值由内核态改变，用户只能通过 P/V 控制；int 可在用户态修改。做题判定只看一条：**会不会阻塞**。例：挖坑种树中"坑数不超过 3""有坑才能种树"都是阻塞条件 → 两个信号量，很多人直接上 int 而丢分。

> **易错点**：把阻塞条件写成 `if` + int；或反过来把纯分支判断写成信号量。
> **注意**：第 ② 条是判定用信号量还是辅助变量的根本依据，也是本节最重要的结论。

## 理发师问题：分支条件与阻塞条件的判定

[01:52:00 - 02:02:00]

一位理发师、一把理发椅、n 把等候椅；无顾客则理发师睡觉；顾客到来须叫醒理发师；理发师忙时顾客有空椅则坐等，无空椅则离开（"离开"即进程结束）。判定："有无空椅"是分支 → `chairs`（int，初值 n）+ 保护它的 `mutex`；"无顾客则睡觉"是阻塞 → `customer`（初值 0）；"理发师在工作则顾客等"也是阻塞 → `barber`（初值 0，理完发 V）。顾客流程：`P(mutex); if(chairs>0){chairs--; V(mutex); V(customer); P(barber); 理发; P(mutex); chairs++; V(mutex);} else {V(mutex); 离开}`；两个分支都必须 V(mutex)。

> **易错点**：顾客"坐下来等待"本身不是阻塞，阻塞来自 `P(barber)`（理发师忙）；椅子条件只决定走哪条分支，无论有无椅子都不阻塞。
> **易错点**：if/else 两个分支只在一个分支里 V(mutex)，另一分支会漏放锁。

## 读者-写者（零一版）：写后必须有读

[02:02:00 - 02:18:00]

在原读者-写者上增加条件：写者写的内容还未被任何读者读过时，新写者不能写，即两个写者之间至少要夹一个读者。写者除 `rw` 外还需 `writable`（初值 1，表示"上一个访问者是读者/初始可写"）：`P(writable)` 会阻塞，故它是信号量，不是辅助变量。读者读完是否要 `V(writable)` 取决于"前一个访问者是否为写者"，这个条件不导致阻塞、只决定是否 V，所以用辅助变量 `flag`。

读者侧：读完后在 mutex 区间内判断 flag，若为真则 `V(writable)` 并置 flag=false；写者写完置 flag=true。`V(writable)` 只能在前一访问者是写者时执行一次：若"每个读者都 V"或"第一个/最后一个读者 V"，读读交替进出时会被反复 V，使 writable 值大于 1 而失去作用。

> **易错点**：用 int 判断 writable 的值再看要不要 V——信号量不允许读值，只能 P/V。
> **技巧**：flag 的互斥可以"蹭"已有信号量：写者改 flag 在 `rw` 临界区内，读者改 flag 在 `mutex` 临界区内，无需新增锁。

## 先进先出（公平）模型

[02:18:00 - 02:27:00]

公平策略要求先申请进入共享区的进程先进入，读者不再享有"后来者直接跟入"的优势。实现只用一个 `queue`（初值 1）：在**开始申请资源之前** P(queue)，在**已取得不可被超越的先发优势之后**立即 V(queue)，而不是放在临界区末尾。读者-写者公平版中，读者与写者都在成功 `P(rw)` 之后 V(queue)——此时读者已拿到锁、后来的写者抢不到，写者已独占、后续读者进不来，后来者"为时已晚"。整套改造只在原代码上加四行。

> **易错点**：把 V(queue) 放到进程末尾 → 退化成普通互斥，失去并发；过早 V → 未取得先发优势，公平性失效。

## 单向阻塞模型：高优先级进程的"底牌"

[02:27:00 - 02:42:00]

用于"A 对 B 有绝对优先级"：只要 A 到来，B 全部等待，A 可插到所有尚未申请资源的 B 之前。实现：`queue`/`mutex` 初值 1，B 侧每个进程进入前 `P(q)`、通过后立即 `V(q)`，使同一时刻只有一个 B 能与 A 竞争，且 B 拿到 q 后马上释放让后续 B 继续推进；A 侧借用读者计数思路（第一个 A `P(q)`、最后一个 A `V(q)`）避免 A 自我阻塞。于是 A 只需释放一次，B 之间链式互相释放。模板用法：把高优先级进程代码放入 A 位、低优先级放入 B 位即可。典型应用是写者优先：有写者在等待时新读者不得进入，直接套模板。

> **易错点**：让 B 也去做"第一个 P、最后一个 V"的计数 → B 之间互相阻塞，模型失效。

> ⚠️ **需回看视频 [02:32:00]**：讲解中 P1/P2 与 PR/PE 两套称呼混用，模板代码的 P/V 落点难以与口述一一对应，需对照板书确认 —— "我P一它只负责卡死第一个P二，然后我第一个P二负责用这个互斥信号量把后面的P二全部都卡死了"

## 哲学家就餐（加碗）真题：资源分配图破环

[02:42:00 - 02:48:00]

圆桌 5 位哲学家，每人须取得一个碗和两侧筷子才能进餐。普通解法（都先左后右取筷）在资源分配图上形成环，即循环等待。破环：改变部分哲学家的取筷顺序（如奇数号先右后左、偶数号先左后右），环被打断。再加入碗时，规定"每人必须先取碗、再取筷子"，于是碗只有出边、没有入边，不可能构成新环。故本题两步：破筷子的环 + 固定碗在最前，其余与基础课解法相同。

> **易错点**：允许不同人取碗/取筷顺序不同，就会出现指向碗的边，可能重新成环。

> ⚠️ **需回看视频 [02:45:00]**：破环时对具体改哪条边的叙述前后不一致（"一号先申请一再申请四"与其原顺序"先取四再取一"矛盾），需结合图示确认 —— "让他先，让一号先申请一再申请四，让三号先申请三再申请二"

## 生产者-消费者真题：一个消费者连续取十件

[02:48:00 - 02:52:00]

1000 件产品的缓冲区，新增条件：某消费者连续取出 10 件后其他消费者才能取。这是**消费者对消费者**的阻塞，对生产者无影响，因此不能复用全局 mutex（它管的是所有进程对缓冲区的互斥），要新设 `c_mutex`（消费者互斥，初值 1）。消费者先 `P(c_mutex)`，再循环 10 次（每次 `P(full); P(mutex); 取; V(mutex); V(empty)`），十次结束后 `V(c_mutex)`；外层最好用 `while(1)` 包住。

> **易错点**：用原 mutex 实现"连续取十件"，会把生产者也挡在外面且无法阻止其他消费者插入；漏写外层循环。

## 信号量的特性与选择题考点

[02:52:00 - 02:57:00]

信号量特性：P 在 S ≤ 0 时使进程阻塞（让权等待，进入阻塞态）；V 唤醒一个阻塞在该信号量上的进程；信号量自带等待队列且先进先出，因此可实现 FIFO 与让权等待。选择题辨析：S 为负并不表示"所有申请者都维持阻塞"（S 从 -4 变 -3 时已唤醒一个，且未回到正值）；自旋锁不满足让权等待（进程在运行态/就绪态间交替）；非抢占调度下 V 不改变当前进程状态；非抢占调度下 P 可能阻塞当前进程，但不是"进入就绪态"。

> **易错点**：把"P 阻塞"说成"进入就绪态"；把自旋锁的忙等当成让权等待。

## 整型信号量的 wait/signal 实现（开关中断）

[02:57:00 - 03:04:00]

真题常用 `wait`/`signal` 表示 P/V，答题时需与题目用语一致。信号量 S 有写操作，故其访问必须互斥。方法一：关中断后 `while(S<=0);` 空转——关中断期间无法进程切换，没有人能执行 signal 把 S 改大，系统死等，错误。方法二：在循环体内先开中断再关中断，留下可被调度的窗口，其他进程得以执行 signal 使 S>0，本进程恢复后跳出循环，正确。用户程序不能用开关中断实现临界区：开关中断是特权指令，只能在内核态执行。

> **易错点**：认为"关中断 + while 等待"可行——关中断恰好切断了唯一的救援路径。

## 硬件方法：TestAndSet 与自旋

[03:04:00 - 03:08:00]

`TestAndSet` 是硬件原语，执行期间不会被打断。用法：`while(TestAndSet(&lock));` 临界区; `lock=false;`。它通过死循环阻止进入，不涉及阻塞与唤醒，进程在就绪态与运行态之间交替，谁能在 lock 变 0 的瞬间被调度上 CPU 全看运气。因此它不能实现先进先出、不满足让权等待，也不节省 CPU 与调度开销。

> **易错点**：把 TSL 说成"阻塞进程"或"可实现 FIFO"——都错，它只是忙等。

## 并发指令序列的取值分析

[03:08:00 - 03:13:00]

两进程对共享变量各执行若干条原子指令时，约束是：同一进程内部的指令顺序不可改变，不同进程的指令可任意交错，任何时刻都可能发生切换。分析方法是枚举交错（穷举）或按切换点分段推演。例：x 初值 1，P1 做加一、P2 做减一，各自 load/运算/store，可能结果为 {0, 1, 2}——丢失更新导致 0，串行执行得 2 或 1。写回顺序不同会得到不同结果，须逐种排列验证。

> **公式**：可能取值集合由"两进程 store 的相对次序 + 中间是否插入对方 load"共同决定，无覆盖写时取串行值。

## 互斥实现方式与同步互斥选择题考点

[03:13:00 - 03:15:00]

互斥的实现途径：软件方法（Peterson 等）、关中断、硬件原子指令（TSL/Swap）、信号量。**原子操作在单处理机与多处理机上都适用且必然互斥；关中断只对单处理机有效，多处理机无效**——这是常见选择题考点。Peterson 算法可用断点分析法验证其满足互斥、有限等待、不饥饿（基础课有专门分析）。

> **易错点**：认为关中断在多处理机上也成立。

## 信号量的物理意义

[03:15:00 - 03:17:00]

信号量初值等于该类资源总数。S > 0 时，S 表示当前可用资源数，此时没有进程等待；S < 0 时，|S| 表示阻塞在该信号量上等待资源的进程数。例：初值 3、当前值 1，则可用资源 1 个、等待进程 0 个；若当前值为 -3，则有 3 个进程在等待。

> **公式**：S = 当前可用资源数 − 等待该资源的进程数（S>0 取前者，S<0 时 |S| 为后者）。

## 死锁预防的四个必要条件

[03:17:00 - 03:18:00]

互斥：资源一次只能被一个进程使用（若资源可共享，如经 SPOOLing 改造的打印机，则不再满足）。请求与保持：进程因请求而阻塞时，对已占资源保持不放。不可剥夺：已获得的资源不能被强行剥夺。循环等待：若干进程形成头尾相接的环形等待，对应资源分配图中出现环。破坏其中任一条件即可预防死锁。

## 死锁概念易错点：死锁避免、银行家算法与死锁检测

[03:18:00 - 03:24:00]

死锁状态一定是不安全状态，但不安全状态不一定是死锁状态；死锁避免的目标就是不让系统进入不安全状态。死锁避免（银行家算法）只决定"这一次请求给不给"，**不限制进程申请资源的顺序**；限制申请顺序属于死锁预防（如按序分配破坏循环等待）。安全序列不是资源分配顺序。银行家算法由两部分组成：先假设分配并修改 available/allocation/need，再做安全性检测（找安全序列）；"不安全状态检测算法"只是其主体，不是全部。死锁检测看各进程**当前 request** 能否满足，安全性检测看各进程**最大需求 max**——真题常在此抠字眼。

> **易错点**：把"安全序列"当成资源分配顺序；把银行家算法等同于安全性检测算法。

## 请求与保持、按 PID 分配破坏循环等待

[03:24:00 - 03:26:00]

破坏请求与保持：要求进程一次性申请全部资源（或申请新资源前释放已占资源）。典型对应关系：信号量的 P 操作即"占有并保持"，资源分配图成环即"循环等待"。若规定多个进程请求同一类资源时优先满足 PID 较小者，则分配图中边恒由小 PID 指向大 PID，必存在拓扑序列、不可能成环，从而破坏循环等待。

> **易错点**：按 PID 分配破坏的是循环等待，不是请求与保持。

## 不死锁所需资源数下限

[03:26:00 - 03:29:00]

思路是构造最坏情况：让每个进程都差一个资源而卡住。n 个进程各需 2 个同类资源时，最坏是每个进程各占 1 个，共 n 个仍可能死锁；再多给 1 个，无论给谁都能让该进程完成并释放，故最少需 **n+1**。三个进程分别需 3、4、5 台设备时，最坏占用 2+3+4=9，再加 1 得 10。

> **公式**：不死锁的最少资源数 = Σ(各进程最大需求量 − 1) + 1。

## 银行家算法大题：need 矩阵、安全检测与请求试分配

[03:29:00 - 03:34:00]

第一问 need = max − allocation，逐进程逐资源相减。第二问安全性检测：以 available 为工作向量，反复寻找 need ≤ available 的进程，假设其完成并回收其 allocation，记入安全序列；能收完所有进程即安全。第三问请求处理：先检查 Request ≤ need 且 Request ≤ available，然后试分配（available −= Request，allocation += Request，need −= Request），再做安全性检测；安全则确认分配，不安全则回滚。板书例题中初始 available=(1,5,2,0)，可得安全序列 P0、P2、P1、P3；P1 请求 (0,4,2,0) 试分配后 available=(1,1,0,0)，仍能找出安全序列，故可分配。

> **方法**：need 矩阵是"还差多少"，available 是"现在有多少"，安全序列只需存在一个即可，不唯一。
> **易错点**：试分配后忘记同步修改 need；把"找得到安全序列"误解为"必须按该序列真实分配资源"。
