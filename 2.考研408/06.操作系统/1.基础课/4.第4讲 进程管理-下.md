# 操作系统基础课 第4讲 进程管理-下

## 进程同步与互斥的基本概念

[00:00:00 - 00:14:00]

本讲是进程与线程的第三次课，内容分两大块：同步互斥与死锁。同步互斥是 408 的重中之重，既可能出 7～8 分的大题（PV 题），也可能在选择题中出现；死锁多以选择题形式出现。多道程序并发执行时，执行先后次序不确定，但某些任务要求进程按特定次序推进（同步），而有些资源一次只允许一个进程使用（互斥），因此操作系统必须提供同步与互斥机制。

> **定义**：临界资源——一次仅允许一个进程使用的资源（打印机、输入机、磁带机等物理设备都是典型例子）。
> **定义**：临界区——访问临界资源的**程序片段（代码）**，不要与临界资源（资源本身）混淆。
> **定义**：原子操作——不会被进程调度机制打断的操作，一旦开始就一直运行到结束，中间不发生进程切换。
> **定义**：锁——保证进程持续运行的机制，只有第一个申请到锁的进程能继续运行，其他申请者被阻塞并进入该锁的阻塞队列；其本质是"一位内存 + 一个阻塞队列 + 申请锁/释放锁的方法"组成的数据结构（这里指会阻塞的锁，另有自旋锁）。
> **易错点**：原子操作存在的根本原因是时间片轮转调度使指令之间随时可能被打断；把一系列操作封装为原子操作后，处理机在该区间内不会被切换。

## 进程同步的实例：前驱制约关系

[00:14:00 - 00:16:00]

以计算 2×3 + 2×(2×3) 为例，A 进程负责 a=2、b=3，B 进程负责 s1=a×b，A 再算 s2=2×s1，B 最后算 s=s1+s2。若无任何约束，A 可能在 B 完成 s1 之前就执行 s2，得到错误结果。同步的实质就是对各进程指令执行次序施加制约，保证"B 先算 s1、A 再算 s2、B 最后求和"这样的先后关系。

> **易错点**：同步是"有先后次序要求"的协作关系，互斥是"不能同时进入"的排他关系，两者常同时出现在一个题目里，但含义不同。

## 临界区的四个部分与四条访问规则

[00:16:00 - 00:19:00]

与临界区相关的代码被分为四段：进入区（进入前的准备，用于保证临界区性质）、临界区（访问临界资源的代码）、退出区（离开时做善后，使其他进程可以进入）、剩余区（其余代码）。考试要求设计的主要是进入区与退出区。临界区访问必须满足四条规则，这些规则常被直接作为选择题选项出现。

> **定义**：空闲让进——没有进程在临界区时，任何想进入的进程都可以进入。
> **定义**：忙则等待——已有进程在临界区时，其他进程均不能进入。
> **定义**：有限等待——等待进入临界区的进程不能被无限期拖延（否则产生饥饿）。
> **定义**：让权等待——不能进入临界区的进程应释放 CPU、转入阻塞态。该条为**可选**条件，但用信号量做 PV 操作时必须满足。

## 软件同步方法的由来与执行顺序计数

[00:19:00 - 00:26:00]

408 的软件同步只考两个进程（P0、P1），基本思路是让两个进程共享某些变量来协调行为。问题的根源是进程调度（尤其时间片轮转）：任一进程都可能在执行任意一条指令后被抢占，于是多个进程访问临界区时，指令交错顺序不同就会得到不同结果。关键性质是：**进程内部的执行次序不会逆转，进程之间的切换随机发生**——这正是后面所有分析方法的基础。

> **公式**：每进程 3 步、共 2 个进程时，可能的交错执行顺序数为 6!/(3!·3!) = 20 种（6 为总步数，两个 3! 分别消去各进程内部的排列）。
> **易错点**：进程并发切换不是"设计好的"，而是调度算法带来的不可预测性；用户程序必须按"任何时候都可能切换"来设计。

## 两条分析思路：穷举法与断点分析法

[00:26:00 - 00:28:00]

穷举法利用"进程内次序不变、进程间随机切换"，把所有可能的执行顺序列全，逐一检查是否满足条件。另一种是断点分析法：先按四个条件确定"该看什么状态"，再把断点打在能代表该状态的那条指令之后做推理，速度快但需要训练；只掌握穷举法也足以应付真题（真题规模不大）。

> **易错点**：`while (表达式);` 这种写法在软件同步代码中很常见，含义是"表达式为真时原地空转"，即通过忙等把进程卡在进入区，而不是让它阻塞睡眠。

## 四个条件的检验方法与"饥饿"的严格含义

[00:28:00 - 00:34:00]

检验忙则等待：让 P1 停在临界区内，看 P2 能否通过进入区的循环；反向再验一次，两个方向都进不去才算互斥成立。检验空闲让入：一看两个进入区的条件能否同时为真（若能，则双方都卡死）、二看只有单个进程时它能否再次进入（有的实现第一次能进、第二次要依赖对方才能进）。检验有限等待：一个进程已在临界区、另一个卡在进入区，此时**新来的同类进程**是否必然抢先。

> **定义**：饥饿——P1 已卡在进入区等待，若新来的 P2 竞争资源时**必然**（不是"可能"）比 P1 先进入临界区，且这种情况可不断重复，则称 P1 被饥饿，即不满足有限等待。
> **易错点**：判定饥饿的两个要点是"原进程已经卡在进入区最后一步"和"新来者必然抢先"，"可能抢先"不算饥饿。

> ⚠️ **需回看视频 [00:33:00]**：老师在此处连续口误更正，饥饿与不满足有限等待的对应关系表述反复 —— "这样才叫有限等待，这样才叫，不是，这样才叫不满足有限等待，才叫饥饿"

## 三次失败的尝试与 Peterson 算法

[00:34:00 - 00:44:00]

第一次尝试用 turn 表示"允许谁进入"：turn 初值为 1 且 P1 没来时，P0 永远进不去，不满足空闲让进。第二次尝试用 flag 表示"对方是否在临界区"，先检查后置位——检查与置位之间可能被切换，双方可同时通过，破坏忙则等待。第三次尝试让 flag 表示"我想进"，但双方同时置位后会互相等待，两人都被卡住，不满足空闲让入。Peterson 把两者结合：置 flag[i]=true 表示想进，再把 turn 让给对方，然后 `while (flag[j] && turn == j);` 等待，退出时 flag[i]=false。

> **易错点**：408 不考"如何从零设计出 Peterson 算法"，只考"给定进入区/退出区，分析它是否满足四个条件"；分析能力才是得分点。

## 穷举法验证 Peterson 算法

[00:44:00 - 00:50:00]

把 P0 的四条语句编号 1～4、P1 的编号 5～8，从"先执行 1 还是先执行 5"开始画树，每个节点按"这条指令后是否切换"分成两支，叶子节点就是一条完整执行序列（退出那一步不影响结果，可不再展开）。利用对称性（先 1 与先 5 对称）可只分析一半。例：序列 1-2-5-6-3 中，P0 执行到 3 时 flag1=1 但 turn=0，故可进入；随后 P1 执行 7 时 flag0=1 且 turn=0，被挡住——满足忙则等待与互斥。穷举的缺点是节点数量爆炸，但真题规模下仍可用。

## 断点分析法验证 Peterson 算法

[00:50:00 - 01:02:00]

断点分析法的要点是"按条件选状态、在关键指令后打断点"。忙则等待：把断点打在 P0 刚通过语句 3（位于 3、4 之间），由"P0 能通过 3"必然推出 `flag1=1 且 turn=1` 不能同时成立；分两种情形——turn=0 说明 P1 已过语句 6、正位于 6 与 7 之间，此时 flag0=1 且 turn=0，7 无法通过；flag1=0 说明 P1 尚未开始，追踪其后续路径仍会被 flag0=1、turn=0 挡住。另一种对称情形无需再证。空闲则入：3 与 7 的条件分别含 turn=1 与 turn=0，不可能同时成立，故不会双双卡死；且无 P1 时 flag1 恒为 0，P0 不会自锁。有限等待：P1 退出瞬间 flag1=0，P0 有机会通过，故不会饥饿。让权等待：纯软件方法都是忙等，不能让出 CPU，一律不满足。

> **易错点**：纯软件同步方法（含 Peterson）都**不满足**让权等待，这是它必须被硬件/信号量机制取代的根本原因。

> ⚠️ **需回看视频 [01:00:00]**：有限等待的断点推理结论表述含混，"进栈"疑为 ASR 误识 —— "它是有可能通过竞争，还是一定通过进栈"

## 真题：x 加减操作的竞态与结果

[01:02:00 - 01:22:00]

P1 做 x=x+1（取 x 到 R1、R1+1、R1 写回 x），P2 做 x=x-1（取 x 到 R2、R2-1、R2 写回 x），x 初值为 1。关键前提是**每条指令本身不可被打断**（指令执行完才响应中断，才可能调度）。最终 x 的值只取决于两件事：谁最后写回，以及对方的"读 x"发生在这次写回之前还是之后；四种有效组合给出 x = 2（P1 最后写回且 P2 读到旧值）、1（串行执行，或读写在时间上互不交叠）、0（P2 最后写回且 P1 读到旧值）。

> **易错点**：不能用穷举硬算 20 种排列，抓住"最后一次写回"与"对方读取的时机"两个断点即可；大量排列是重复情形。

> ⚠️ **需回看视频 [01:06:00]**：四种情形的取值推导口述跳跃、数字前后不一致 —— "那么这个情况下，x是是什么？是一……是把零取到R一，然后进行了这些操作，它是一"

## 锁机制与互斥锁的实现

[01:22:00 - 01:27:00]

软件方法的两个缺点是：分析复杂（要考虑所有执行顺序）、必须忙等（浪费 CPU、不阻塞）。锁是更高层的抽象：进程进入临界区前申请锁，离开时释放锁，申请失败则等待。最朴素的互斥锁只有一个 value（0 空闲、1 占用），`while(value==1); value=1;` 加锁、`value=0;` 解锁——但"检查"与"置位"是两条分离的指令，两个进程可能同时通过检查，互斥被破坏。

> **定义**：自旋锁——申请失败时原地反复申请、不进入阻塞态，进程处于运行态/就绪态之间空转。
> **定义**：阻塞锁（无忙等待锁）——申请失败即阻塞并挂到该锁的阻塞队列上，待持有者释放时被唤醒。
> **易错点**：朴素锁实现失效的根因是"测试与设置分离"，因此真正的锁必须借助硬件原子性（关中断或原子指令）。

## 锁的硬件实现：关中断与原子指令

[01:27:00 - 01:32:00]

关中断法：加锁时关中断、解锁时开中断，因为关中断期间不会发生进程调度与切换，所以中间不会被打断；但它只对单 CPU 系统有效，多处理机上其他 CPU 仍可并发访问。原子指令法：现代 CPU 提供一条指令完成"测试+设置"的功能，指令内部不会发生切换。典型指令是 test-and-set（取出内存单元的值并测试，同时将其置 1）和 exchange（原子交换，把中间变量的三步合成一条指令）。

> **易错点**：关中断的有效性来源于"关中断 ⇒ 不能被调度"，与锁本身无关；其局限是只能保护本 CPU。

## 用原子指令实现自旋锁与阻塞锁

[01:32:00 - 01:38:00]

自旋锁：`while (test_and_set(lock.value));` 加锁，`lock.value = 0;` 解锁。正确性在于取值与置位原子完成——后到者看到的必然是 1，于是被挡在外面。但自旋锁**不能实现先进先出**：解锁瞬间谁恰好被调度上 CPU 谁就能进，与到达次序无关。阻塞锁在 test_and_set 失败时把当前进程挂到阻塞队列 q 并调度走，解锁时 value 置 0 并唤醒队首进程，队列天然满足 FIFO。

> **定义**：实现锁的三条途径——关中断、纯软件方法（Peterson）、原子操作指令（test-and-set / exchange）。
> **易错点**："自旋锁不公平"与"阻塞锁公平"的差别只来自阻塞队列，不来自原子指令。

## 信号量的定义、语义与实现

[01:38:00 - 01:45:00]

信号量是操作系统提供的、用于协调共享资源访问的同步机制，地位高于进程。它内部有一个整型值 sem（表示所绑定资源的数量）、一个阻塞队列和 P/V 两个原子操作：P 申请资源（值减 1，减后小于 0 则阻塞入队），V 释放资源（值加 1，加后仍小于等于 0 说明有人在等，唤醒队首）。信号量为负时，其绝对值等于阻塞在该信号量上的进程数。

> **定义**：P 操作——`sem--; if (sem < 0) 阻塞当前进程并入阻塞队列;`；V 操作——`sem++; if (sem <= 0) 唤醒阻塞队列中的一个进程;`。
> **易错点**：信号量初始化完成后**只允许** P、V 两种操作，不能赋值、不能加减、不能判等（写 `S = S - 1`、`if (S == 1)` 都是错的）；信号量只能在内核态由操作系统修改，而 int 型变量用户程序可随意读写。
> **易错点**：P 可能阻塞、V 一定不阻塞；通常假定信号量按 FIFO 公平唤醒。按用途分资源信号量（初值可取任意非负值）与二进制信号量（0/1）。

## 用信号量实现互斥与同步

[01:45:00 - 01:49:00]

互斥：设 mutex 初值为 1，临界区前 P(mutex)、临界区后 V(mutex)。第一个进程进入后 sem 变 0，其余进程阻塞在临界区入口，直到持有者 V 操作唤醒一个。同步（规定先后次序）：设初值为 0 的信号量，在前驱动作之后 V、在后继动作之前 P，这样后继动作在信号量被 V 之前必然被阻塞；多个前驱关系就用多个信号量。

> **易错点**：互斥中 P、V 的次序不能颠倒、不能重复、不能遗漏；同步中"前 V 后 P"的位置由前驱关系决定，与临界区无关。

## 生产者-消费者问题与 PV 公式法

[01:49:00 - 02:10:00]

生产者把产品放入缓冲区，消费者从中取出。缓冲区必须互斥访问；同时生产者需要"有空位"才能放，消费者需要"有产品"才能取。公式法四步：①写出不考虑同步互斥时每个进程的行为序列；②对每个行为列出"能继续执行（不阻塞）的条件"并写成不等式；③移项成 `s > 0` 的形式；④把每个 s 设为一个信号量并确定初值，凡某行为使 s 减小就在它**前面**加 P，凡使 s 增大就在它**后面**加 V。据此得到：互斥条件 `1 - 缓冲区进程数 > 0` → mutex=1；`空位数 > 0` → empty=n（放产品前 P）；`产品数 > 0` → full=0（取产品前 P）；放产品后 V(full)+V(mutex)，取产品后 V(empty)+V(mutex)。

> **易错点**：P(mutex) 必须放在 P(empty)/P(full) **之后**。若先 P(mutex) 再 P(empty) 失败，生产者会"持锁自锁"，消费者进不来腾不出空位，双方互锁形成死锁。
> **易错点**：V 操作的先后顺序无所谓，因为 V 永不阻塞；P 的顺序则决定会不会死锁。

## 带条件分支的 PV 问题：读者-写者

[02:10:00 - 02:24:00]

读者-写者问题：多个读者可同时读，写者与写者、写者与读者互斥。引入一把读写锁 rw：写者 P(rw)…V(rw)。读者则出现分支——**第一个读者**要代表全体读者 P(rw)，后续读者直接进入；**最后一个读者**退出时才 V(rw)。因此需要引入计数器 count（初值 0）并以 mutex 保护：`P(mutex); if (count==0) P(rw); count++; V(mutex);` 读文件；`P(mutex); count--; if (count==0) V(rw); V(mutex);`。

> **易错点**：不是所有读者都释放 rw，只有最后一个读者（count 减到 0）才释放；若每个读者都 V(rw)，信号量会失去意义。
> **易错点**：count 是共享变量，对它的读、改、判断必须全部包在同一对 P(mutex)/V(mutex) 之内。

## 两类条件的判别：不阻塞条件与分支条件

[02:24:00 - 02:29:00]

PV 题中只存在两类条件，判别它们决定了用信号量还是用 int 辅助变量。第一类是"不阻塞条件"：不满足就会阻塞（如申请不到 rw 锁），它对应一个信号量，由不等式移项得到。第二类是"分支条件"：无论满足与否进程都继续执行，只是走不同路径（如"我是不是第一个读者""有没有空椅子"），它对应一个 int 型变量 + if 语句。

> **易错点**：信号量与 int 变量的三条区别——信号量只能初始化/P/V，int 可任意算术、判等、赋值；信号量在内核态由 OS 维护，int 由用户程序直接修改；信号量不满足条件会引起阻塞，int 只改变执行路径。这是全书 PV 题的核心判据。

## 读者-写者进阶：限制同时读者数

[02:29:00 - 02:32:00]

若要求同时最多 4 个读者，就在读操作前再加一个不阻塞条件："已经在读的进程数 r < 4"，移项得 `4 - r > 0`，设信号量 rmax 初值为 4；读之前 P(rmax)、读之后 V(rmax)。判断是否带等号的方法：站在**正要进入**的进程角度，已有 r 个读者，只有 r < 4 才允许它进入，所以是严格小于。

> **易错点**：不等式的等号取舍看"请求者进入前一刻的已有数量"，写成 r ≤ 4 就等于允许 5 个读者同时读。

## 理发师问题：int 与信号量的实战判别

[02:32:00 - 02:42:00]

一位理发师、一把理发椅、n 把等待椅。顾客到来时若理发师空闲则唤醒他，否则若有空椅就坐下等，没空椅就离开。"有没有空椅子"是**分支条件**——有空椅就坐下等待、没空椅就离开，两条路都不阻塞（离开是进程终止，不是阻塞），故用 int 计数器 chairs=n + mutex 保护，`if (chairs==0) 离开; else { chairs--; ... }`，且 P(mutex) 在主分支上、每个分支末端都要 V(mutex)。"没有顾客则睡觉"是**阻塞条件**（睡觉=停下来等人叫醒），用信号量 customer 初值 0。"理发师正在工作则顾客休息"同样是阻塞条件，用表示"空闲理发师数>0"的信号量（初值 1），理发前 P。

> **易错点**："离开"不是阻塞而是进程结束，所以"有没有空椅"绝不能用信号量；"睡觉/休息"这类词是阻塞语义的标志词。

## 用信号量实现先来先服务（FIFO 模型）

[02:42:00 - 02:46:00]

要让被阻塞的进程按到达顺序被唤醒，可设一个初值为 1 的排队信号量 que：每个进程在核心操作前 P(que)，在核心操作完成后 V(que)。由于 que 初值 1，同一时刻只有一个进程能进入操作区；该进程完成核心操作（KOP）后才 V(que)，从队列中放出下一个进程，于是核心操作严格按 FIFO 执行。此模型强化课再展开。

> **易错点**：V(que) 必须放在核心操作**之后**，放在之前就退化为普通互斥，无法保证执行顺序。

## 管程的组成与条件变量

[02:46:00 - 02:50:00]

管程是面向对象的多线程互斥方法，任意时刻最多只有一个线程执行管程代码。它由一把锁（保证进入管程的互斥）、若干共享变量和多个条件变量组成。条件变量对应一个**阻塞条件**：条件不满足时调用 `x.wait()` 无条件阻塞当前进程并挂到该条件变量的等待队列（num_waiting 计数加 1），条件满足时调用 `x.signal()` 唤醒队列中的一个线程（队列为空则什么也不做）。

> **定义**：wait——无条件阻塞（阻塞条件已在调用前用 if/while 判断好），并释放管程锁；signal——唤醒该条件变量等待队列上的一个进程，队列空时为空操作。
> **易错点**：管程内部的所有条件判断都用普通 int 变量 + if/while 完成，阻塞动作统一交给 wait，不需要再区分"分支条件"与"阻塞条件"。

> ⚠️ **需回看视频 [02:47:00]**：此处口述的"条件变量的 C++ 操作"显然是 ASR 误识，应为"signal 操作" —— "C++操作，一个叫条件变量的C++操作，它就是把等待队列中的一个线程给唤醒"

## 用管程解决生产者-消费者问题

[02:50:00 - 02:56:00]

管程内维护 count（缓冲区产品数）和两个条件变量：notFull（缓冲区非满，生产者放产品的条件）、notEmpty（缓冲区非空，消费者取产品的条件）。由于管程本身保证互斥，不再需要额外的 mutex。生产者：`if (count == n) notFull.wait(lock);` 放产品、count++、`notEmpty.signal();` 消费者：`if (count == 0) notEmpty.wait(lock);` 取产品、count--、`notFull.signal();`。

> **易错点**：wait 的调用前必须用 if/while 判断条件（wait 本身不做判断），而 signal 内部会自行判断队列是否为空，不需要外加 if。

## 管程释放锁的细节与信号量对比

[02:56:00 - 03:02:00]

`notFull.wait(lock)` 要传入管程锁，原因是被阻塞前必须把锁释放掉：否则生产者持锁睡去，消费者进不来腾不出空位，形成死锁。被唤醒后进程重新申请锁继续执行。信号量与管程的对比：信号量由操作系统支持（系统调用/原语），由临界区**使用者**自己保证正确性；管程由编程语言/库提供（函数调用），由资源**提供者**封装好接口。阻塞条件上，信号量是"值 ≤0 时执行 P 被阻塞"，管程是"条件变量 wait 必阻塞"；唤醒条件上，信号量"值 <0 时 V 才唤醒"，管程"等待队列非空时 signal 才唤醒"。二者功能等价，条件变量底层由信号量实现；复杂问题用管程更易写。

> **易错点**：对比表里的唤醒条件应理解为"信号量值 ≤ 0 时执行 V 才会唤醒等待者"（视频此处表述前后不一，按 ≤0 记忆）。

> ⚠️ **需回看视频 [02:59:00]**：信号量阻塞/唤醒的临界值与上文"≤0"表述冲突 —— "计数值为负的信号量执行v操作，对吧？并不是所有的v操作都会唤醒进程"

## 死锁的定义、资源类型与资源分配图

[03:02:00 - 03:06:00]

死锁指两个或多个进程因竞争资源而互相永久等待、无法推进的状态（如两车相向互不相让）。进程访问资源分三步：请求、使用、释放，且释放通常在进程全部任务完成后才发生，这正是死锁滋生的土壤。资源分两类：可重用资源（处理器、I/O 通道、存储器、文件、数据库、信号量等，可反复使用）与消耗型资源（用一次即耗尽）。资源分配图用圆圈表示进程、方框内的小点表示资源实例，进程→资源的边是请求边，资源→进程的边是分配边。

> **易错点**：资源分配图中出现环是判断死锁的关键信号；单个实例的资源类出现环即死锁，多实例时环只是"可能死锁"。

## 死锁的四个必要条件

[03:06:00 - 03:08:00]

互斥（一个资源实例同一时刻只能被一个进程占用）、持有并等待（进程持有至少一个资源且不释放，同时又去申请其他资源，"吃着碗里的望着锅里的"）、非抢占（资源只能由持有者自愿释放，不能被强行剥夺）、循环等待（存在 P0→P1→…→Pn→P0 的环形等待链，如 P0 占 A 求 B、P1 占 B 求 C、P2 占 C 求 A）。

> **易错点**：这四个是**必要条件而非充分条件**——四个条件同时成立只是"可能"死锁，不必然死锁。

## 死锁的三种处理策略与死锁预防

[03:08:00 - 03:12:00]

三种策略：死锁预防（事前破坏必要条件，使系统永不进入死锁）、死锁避免（每次分配前判断，只批准不会导致死锁的请求）、死锁检测与恢复（允许发生，事后检测并恢复）；实际系统多用第三种。预防的四种手段分别破坏一个条件：互斥——把独占资源改造为可同时访问（如 SPOOLing 虚拟设备）；持有并等待——要求进程一次性申请全部所需资源（要么全给、要么一个不给）；非抢占——申请不到就立即释放已占资源，或仅在能一次获得全部资源时才分配；循环等待——给资源编号，强制所有进程按编号递增顺序申请。

> **易错点**：破坏循环等待最实用（按序申请），破坏互斥往往做不到（资源本身特性决定），破坏"持有并等待"会降低资源利用率。

## 信号量中的死锁预防与哲学家就餐问题

[03:12:00 - 03:19:00]

信号量本身也是一种资源，它天然满足互斥（一个实例只能被一个进程 P 到）、持有并等待（可以 P 完一个再 P 另一个）、非抢占（不 V 就不会释放）三条，因此只能靠破坏循环等待来防死锁——这正是生产者-消费者中"P(mutex) 放最后"的原因。哲学家就餐：n 人围坐、n 根筷子（信号量数组，初值均为 1），每人需同时拿到左右两根；若都"先左后右"，则每人都持有一根并等待下一根，资源分配图成环 → 死锁。解决：让奇数号哲学家先右后左（或让其中一人反序），环被破坏即可。

> **易错点**：判定与解决都落在"资源分配图有没有环"上；只要申请顺序中无环，即便前三个条件成立也不会死锁。

## 死锁避免与安全状态

[03:19:00 - 03:24:00]

死锁避免要求进程预先声明最大资源需求，在每次分配时动态检查分配后的状态是否安全。安全状态：存在一个进程完成序列，使得按该顺序逐个满足各进程的剩余需求、进程完成后归还全部资源，最终所有进程都能完成。安全状态一定无死锁；不安全状态可能死锁（也可能不）；因此策略是保证系统**永不进入不安全状态**。

> **定义**：安全序列——能依次满足所有进程资源需求的进程排列；存在安全序列即处于安全状态。
> **易错点**：不安全 ≠ 已死锁，只是"可能"死锁；安全状态也可能因进程实际请求方式不同而出现资源闲置。

## 银行家算法的数据结构与安全性算法

[03:24:00 - 03:31:00]

系统有 n 个进程、m 类资源：Max 为 n×m 的最大需求矩阵，Allocation 为 n×m 的已分配矩阵，Need = Max − Allocation 为尚需矩阵，Available 为长度 m 的向量（各类资源剩余量）。安全性算法：令 Work = Available、Finish 全为 false；反复寻找满足 `Finish[i]==false` 且 `Need[i] ≤ Work`（逐分量比较，各类资源都要够）的进程 i，找到则令 `Work += Allocation[i]`、`Finish[i]=true`；若所有 Finish 都为 true 则安全（被选中的顺序即安全序列），否则不安全。

> **公式**：Need[i][j] = Max[i][j] − Allocation[i][j]；进程完成后回收 Work = Work + Allocation[i]。
> **易错点**：`Need[i] ≤ Work` 是向量逐分量比较，任一分量不满足就不能选该进程；回收时加的是 Allocation 而不是 Need。

## 银行家算法的主流程与两种输出

[03:31:00 - 03:37:00]

触发点是某进程发出请求向量 Request_i。第一步：若 `Request_i > Need_i`，说明请求超出此前声明的最大需求，报错；第二步：若 `Request_i > Available`，资源不够，请求者等待；第三步：**试探性**分配（Available −= Request、Allocation += Request、Need −= Request），调用安全性算法；若安全则正式分配，若不安全则回滚这三处修改并拒绝请求。

> **易错点**：银行家算法的输出只有两种——允许分配 / 拒绝分配。安全序列、安全状态都是内部推演过程，不对外输出（很多同学误以为"输出安全序列"）。

## 银行家算法示例

[03:37:00 - 03:42:00]

示例一（4 进程、3 类资源）：初始 Available 只能满足 T2 的 Need，先让 T2 完成并回收其 Allocation，Available 增大后其余进程均可依次完成，得到一个安全序列 T2→T1→T3→T4，故系统安全。示例二：T1 请求 (1,0,1)，试探分配后 Available 变为 (0,0,1)，此时找不到任何满足 Need ≤ Work 的进程，安全性检测失败，于是回滚并拒绝该请求。

> **易错点**：判断"能否分配"必须走完整个安全性检测，只检查"当前 Available 够不够"是不够的。

## 死锁检测与死锁恢复

[03:42:00 - 03:52:00]

死锁检测基于资源分配图，定期运行检测算法判断图中是否存在死锁，其流程与安全性算法类似，但用 Request（进程**实际**发出的请求）替代 Need（进程声明的**最大**可能需求）：Work = Available，反复找 `Request_i ≤ Work` 的进程并回收其 Allocation，全部可完成则无死锁，否则存在死锁。检测时机一般按间隔进行，依据是死锁发生频率、需回滚的进程数等；资源图可能存在多个环，难以定位关键进程。恢复手段：终止进程（全部终止代价过大、少用；一次终止一个直到解除、最常用）、资源抢占、进程回滚（可能引起饥饿）。选择牺牲者的依据包括优先级、已运行时间、已占用资源量、尚需资源量、终止进程数目、交互式还是批处理。课后练习：用 FIFO 模型实现"读写公平"的读者写者问题。

> **易错点**：检测算法用 Request、避免算法用 Need，这是两者的唯一实质差别；Request 已发生，不满足就会立刻死锁，Need 只是上限估计。
> **易错点**：恢复时优先终止"优先级低、已运行时间短、占用资源多、还需资源多、批处理型"的进程，且尽量少终止。
