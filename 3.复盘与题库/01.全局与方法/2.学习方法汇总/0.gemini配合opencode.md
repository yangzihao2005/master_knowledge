## 一、工程环境
### 新建项目脚本
这个脚本一次性帮你把“防 Agent 卡顿”（`.opencodeignore`）、“防版本库臃肿”（`.gitignore`） 和“规范输入口”（`specs/`） 全部配齐了。以后新建任何项目，只要敲一行 `init-ai 项目名`，就能直接在这个标准环境下开工。init-ai.cmd

```
@echo off
setlocal

:: If parameter provided, create and enter folder
if not "%~1"=="" (
    if not exist "%~1" mkdir "%~1"
    cd /d "%~1"
)

:: 1. Create specs directory
if not exist specs mkdir specs

:: 2. Write .gitignore
(
echo .git/
echo node_modules/
echo __pycache__/
echo dist/
echo build/
echo *.tmp
echo *.log
echo *.docx
echo *.pdf
) > .gitignore

:: 3. Copy to .opencodeignore
copy /y .gitignore .opencodeignore >nul

:: 4. Git init
git init -q

echo ==============================================
echo [OK] AI Workspace initialized successfully!
echo - Created: specs/
echo - Created: .gitignore and .opencodeignore
echo - Ready: git repository
echo ==============================================
```

## 二、交付转换
### AI操作word文档
**坚决不让 Agent 写 Word，AI 只负责输出干净的 Markdown，格式转换交给确定性工具 Pandoc**。

```
if not exist "%APPDATA%\pandoc" mkdir "%APPDATA%\pandoc"
pandoc -o "%APPDATA%\pandoc\reference.docx" --print-default-data-file reference.docx
```

在你的用户应用目录下自动建好 `pandoc` 文件夹。将默认模板完整提取到 `%APPDATA%\pandoc\reference.docx`，**完全不会有权限报错**。
之后用:%APPDATA%\pandoc\reference.docx就可以配置目标中的word格式了。

建立md2docx.cmd
因为 Pandoc 已经能自动识别 `%APPDATA%\pandoc\reference.docx`，转换脚本变得极其轻巧，也不用再硬编码引用路径了。

```
@echo off
setlocal

if "%~1"=="" (
    echo Usage: md2docx ^<input.md^> [output.docx]
    echo Example: md2docx report.md
    exit /b 1
)

set "INPUT_FILE=%~1"
set "OUTPUT_FILE=%~dpn1.docx"

if not "%~2"=="" (
    set "OUTPUT_FILE=%~2"
)

if not exist "%INPUT_FILE%" (
    echo [Error] File not found: %INPUT_FILE%
    exit /b 1
)

:: 临时将输入文件转为标准的 UTF-8，防止 GBK 乱码
powershell -NoProfile -Command "$content = Get-Content -Path '%INPUT_FILE%' -Raw; [System.IO.File]::WriteAllText('%INPUT_FILE%', $content, [System.Text.Encoding]::UTF8)"

:: Pandoc 转换
pandoc "%INPUT_FILE%" -o "%OUTPUT_FILE%"

if %ERRORLEVEL% equ 0 (
    echo ==============================================
    echo [OK] Word document generated successfully!
    echo Output: %OUTPUT_FILE%
    echo ==============================================
) else (
    echo [Error] Pandoc conversion failed.
)
```

## 三、AI工作流
核心环节：打通"Gemini网页端-->OpenCode"
以前工具割裂的本质：网页端输入的东西，本地Agent"吃不消"；本地Agent跑出来的半成品，又不知道去哪里验收。

**把 Gemini 网页端变成你的“需求架构师”，让它只输出可以直接存为 `specs/xxx.md` 的规范文件**。

### 1. 为 Gemini 网页端配置“架构师 Prompt”（或自定义 Gem）

在 Gemini 网页端规划任务时，在你的提问末尾加上这句话（或者直接建一个专用的 Gem）：

> **提问结尾固定加上：** “请将最终方案输出为唯一的 Markdown 代码块，作为本地 Agent 的任务规格书（Task Spec），第一行为文件名（形如 `# specs/xxx.md`），内部必须包含：
> 
> 1. `[目标与产出]`（明确要写什么文件，如 `output.md` 或 `main.py`）
>     
> 2. `[输入材料]`（需要读取哪个文件或上下文）
>     
> 3. `[分步执行指令]`（3~5 步原子操作，每步边界明确）
>     
> 4. `[验收标准]`（如何判断任务做对了） 不需要其他寒暄或冗余解释。”

示例：Gemini 网页端会输出这样的标准格式

```
# specs/data_report.md

## 1. 目标与产出
- 目标：将 raw_data.csv 进行数据清洗，并生成完整的分析报告
- 产出文件：`analysis_report.md`

## 2. 输入材料
- 读取当前工作区的 `data/raw_data.csv`

## 3. 分步执行指令
- Step 1: 编写 Python 脚本计算各维度的总和与均值。
- Step 2: 将关键统计结论以标准 Markdown 表格形式写入 `analysis_report.md`。
- Step 3: 根据数据生成 3 条业务洞察总结。

## 4. 验收标准
- 根目录下存在格式规范的 `analysis_report.md`。
- Markdown 表格对齐无误，无代码执行报错。
```

### 2. 本地投喂动作（只需 3 秒）

1. 在网页端点击代码块右上角的 **“复制”**。
    
2. 打开本地项目，在 `specs/` 目录下粘贴保存为 `specs/data_report.md`。
    
3. 打开 OpenCode，新建一个空白会话，发送：
    
    > `@specs/data_report.md 请严格按照该规格书执行，完成后提醒我验收。`
    
    用法：md2docx 你的文件名.md
